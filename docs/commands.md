# Command language

This reference describes the implemented player commands and recorded authority outcomes. The
[rules reference](rules.md) defines their game effects. Legal choices depend on the current phase,
actor, resources and pending decision; accepting the syntax does not make an action legal.

## Text and identifiers

The command input and authenticated command API take the command alone, for example `buy-tokens 4`.
They also accept a registered player id or assigned capital prefix, such as `p1: buy-tokens 4`
or `venice: buy-tokens 4`; the prefix must identify the authenticated seat. Engine callers can use
`TextCodec.parseAction` with state to resolve the same input. Without authentication or a prefix,
that parser requires exactly one prompted player; simultaneous decisions require an explicit actor.
A replay action prefixes it with the registered player id and a colon: `p1: buy-tokens 4`.
Authority outcomes start with `!` and are generated by the server, never submitted as player actions.
Each replay entry occupies one line. Canonical command names and enum values are lowercase; advance
letters are uppercase. Arguments are whitespace-separated, without quoting or comments.

| Placeholder | Meaning |
| --- | --- |
| `<player>` | Registered player id, `p1` through `p6`; independent of the chosen capital or display name. |
| `<capital>` | Available catalog id: `venice`, `genoa`, `barcelona`, `paris`, `london`, or `hamburg`. Starting player count restricts availability. |
| `<reference>` | Opaque reference to a physical card in the acting player's hand, such as `hand-4`; it does not encode the card's identity. |
| `<card-id>` | Catalog identity of a history card, such as `stone-1`; only authority outcomes or revealed plays expose it. |
| `<advance>` | One of the selected table's 26 printed letters, `A` through `Z`. |
| `<commodity>` | `stone`, `wool`, `timber`, `grain`, `cloth`, `wine`, `metal`, `fur`, `silk`, `spice`, `gold`, or `ivory`. |
| `<adjustment>` | `shortage` or `surplus`. |
| `<amount>`, `<spaces>`, `<slot>` | Base-10 integers. Cash amounts are dollars; misery spaces count boxes, not their printed values; slots are one-based. |
| `<die>` | Integer from 1 through 6. |

## Setup and Order of Play

| Command | Who and when; parameter constraints |
| --- | --- |
| `start` | Automatically recorded for the creator during game creation; freezes configuration and requests the opening shuffle and draws. Retained for engine replay. |
| `bid-capital <amount>` | Each player during private capital bidding; integer $0–$40. Bids reveal together. |
| `choose-capital <capital>` | Current capital chooser; the capital must remain available. |
| `buy-tokens <amount>` | Each active player during private Order of Play. Pays the absolute amount, including negative bids; only positive amounts buy pool tokens, capped by stock. Must be affordable in full. |
| `choose-turn-position <slot>` | Current chooser within an equal-purchase group. Insert into slots 1 through the provisional group's size plus 1. |

Games always use three epochs. There is no `set-option epochs` command or `epochs` creation
field. The existing 26th-advance ending can still finish a game before the third deck is exhausted.

### Game variants

The creator chooses variants while registering players. Creation records every resolved value,
then automatically records `start`. Hosted and local application games are already started when
creation returns. The commands below describe engine configuration and replay; they cannot change
an application game after creation.

| Command key (`set-option <key> <value>`) | Values (default first) |
| --- | --- |
| `deck-modification` | `disabled`, `enabled`: exchange `war` and `timber-2-1` between decks 1 and 2 |
| `initial-card` | `any`, `no-crusades`, `no-events`, `commodity-only`; one mutually exclusive opening-deal restriction |
| `immediate-master-art-discard` | `disabled`, `enabled` |
| `map` | `standard` (default), `european`; selects provinces, connections and board drawing |

Initial-deal exclusions remain in the deck for later draws. No preset, improved setup, alternate
advance table, St. Gall support toggle or rebuilt-marker-bonus option is supported. Event-rebuilt
markers use the baseline exclusion from the expansion bonus. See [variants](variant-inventory.md).

## Application history commands

These are authenticated server operations; they are not engine actions and do not accept a player
prefix. Every accepted change records its author and parent revision in immutable history.

| Command | Behavior |
| --- | --- |
| `set-undo-policy <scope>` | Creator before `start`; `competitive`, `regular-turn` (default), `friendly-turn`, or `friendly-game` |
| `undo` | Remove the most recent action when the current scope and recorded outcomes permit it |
| `undo <entry-count>` | Retain this many effective engine entries and validate the removed suffix |

`POST /api/games/{id}/history` accepts `expectedRevision`, zero-based `fromEntry`, and `lines`.
Each line is an ordinary command from the editor or `@<entry-index>` retaining an original action.
Delete/reorder references to remove/reorder actions where the scope permits. The engine must still
accept every retained dependent action and the unchanged recorded outcomes of the same logical
requests. The server never supplies fresh random outcomes for an edit. A rejection leaves history
unchanged; `HISTORY_INVALID_ENTRY` includes a zero-based replacement `entryIndex`.

`GET /api/games/{id}/revisions/{revision}` reads a prior committed revision with the viewer's usual
private-information restrictions. Game file format 5 records normal deltas and explicit suffix
replacements; displayed audit comments are not replayed as engine entries.
Administrative checkpoints retain older revision files in archives. The separate authenticated
[operational API](deployment.md#game-operations-and-programmatic-access) owns log upgrades,
cancellation, abandonment and purge; these are not player commands.

## Turn actions

| Command | Who and when; effect |
| --- | --- |
| `pass` | Current actor; completes cancellation in Draw Card, the actor's Buy Card or Play Cards activity, or an optional Renaissance decision. During Purchase it advances Shipping → Advances → Stabilization or ends Relief. In Expansion it returns unused pool tokens and ends the activity. Zero-cost stabilization and relief without a legal purchase advance automatically. It cannot skip positive-cost stabilization or another required decision. Final Card Play permits passing only after every playable card is gone. |
| `cancel-adjustment <commodity> <adjustment>` | First player before the ordinary draws; removes an existing marker for its commodity's base dollar cost. |
| `buy-card` | Urban Ascendancy owner in Buy Card; once per turn, costs $10 and requests a draw. |
| `discard-card <reference>` | Master Art owner in Buy Card; discards one owned card without effect, once per turn. Independent of buying a card; either order is accepted. |
| `swap-order <player>` | Player answering a Renaissance decision; swap with an adjacent active player who lacks Renaissance. |
| `upgrade-ships` | Shipping purchase step; buys the next eligible upgrade for $10 and proceeds to Advances. At most once per turn. |
| `buy-advance <advance>` | Advances purchase step; buys an affordable unowned advance with its prerequisites and applicable discounts. Repeat as permitted, then `pass`. |
| `stabilize cash` | Positive-cost Stabilization step; pays the hand's stabilization cost in cash. |
| `stabilize misery` | Positive-cost Stabilization step; takes the corresponding misery instead. |
| `relieve-misery <spaces>` | Relief step; buys a positive number of spaces within available current-turn relief rating, advance-tier limit and cash. |

`pass` always answers the current decision or completes the current optional activity. It never
skips another player's response. Purchase steps retain their order even when no purchase is made.

## Expansion and board decisions

| Command | Who and when; effect |
| --- | --- |
| `place <amount> <province>` | Expansion actor; commits a positive number of pool tokens. An attack must commit exactly the calculated requirement, including existing attacker tokens; excess is rejected. |
| `attack <province>` | Expansion actor; calculates and commits the exact additional attack tokens. |
| `reduce-marker <province>` | Expansion actor; replaces an owned coloured marker with one coloured token. A voluntary rebuild never earns expansion-bonus credit. |
| `buy-expansion-card` | Expansion actor; trades pool tokens for one card, at most once per player. Shared price starts at 3 tokens and rises by 3 per purchase this phase. |
| `cathedral` | Eligible attacker or defender before competition dice; declares an automatic win against non-owners. Once per turn against each opponent; cannot defeat a Cathedral-owning defender or apply to War. `pass` declines. |
| `windmill` | Player answering a Wind/Watermill opportunity; requests its selection die. `pass` declines. |
| `offer-card <reference>` | Wind/Watermill trader; selects the owned card to exchange. The other card is chosen by a recorded random transfer. |

`<province>` is a configured province id such as `florence`, not its display name. The engine
chooses a feasible route automatically for the requested token count, preferring non-galley
movement and avoiding shipping when local, land or Caravan movement is usable. Equivalent routes
use deterministic distance and identifier ordering. Reach, overseas access, physical capacity and
remaining per-destination shipping limits still apply. `pass` completes Expansion and returns the
unused pool.

## Card plays and interrupted decisions

| Command | Who and when; effect |
| --- | --- |
| `play <reference>` | Current card-round actor; plays a card requiring no explicit choice. A playable event with no eligible effect may be played without a target. |
| `play <reference> commodity <commodity>` | Selects one of the commodity card's offered commodities. |
| `play <reference> player <player>` | Selects an eligible target player, for example for War. |
| `play <reference> area <area>` | Black Death; a geographical area in play, `i` through `viii`. |
| `play <reference> provinces <province> ...` | Pirates/Vikings in later epochs; distinct eligible coastal markers. Choose the required count, limited by available targets. Text preserves the supplied province order. |
| `play <reference> province <province>` | Selects an eligible target province, for example for Crusades. |
| `play <reference> category <category>` | Papal Decree; category is `science`, `religion`, `exploration`, or `none` to decline a ban. |
| `play <reference> protect <amount>` | Leader play; nonnegative dollars of protection on an exposed leader. |
| `civil-war-loss cash` / `civil-war-loss tokens` | Civil War victim; chooses the loss type. |
| `replace-event-token pool` / `replace-event-token none` | Counter's owner; spend one pool token on replacement or leave the province empty. |
| `cede-war <province> ...` | War loser; names the required distinct eligible provinces, respecting support and overseas limits. Canonical text sorts province ids. |
| `patronize <leader-card-id>` | Eligible Patronage owner during advance purchases; claims an eligible exposed leader and pays its protection once. |
| `forgo-marker` | Recipient of a War/Crusades award with no spare marker; leaves that destination empty. |
| `move-marker <province>` | Same recipient; moves an owned coloured marker from another controlled province to the award, leaving the source empty. |

Only the current card-round actor may play cards, including military cards during their own
War preparation window. Other War participants cannot play cards during someone else's round.

Live input may omit a card's choice qualifier: `play hand-3 cloth`, `play hand-3 p2`,
`play hand-3 alexandria`, `play hand-3 vi`, `play hand-3 religion`, `play hand-3 5`, or
`play hand-3 tunis acre`. The held card determines the choice kind; ordinary rules still validate
the selected value. Explicit qualifiers remain accepted.

A card may also be named by its catalog id or shared name, such as `play stone`,
`play wine/cloth cloth`, or `play crusades alexandria`. Dual commodity names accept either slash
order. Names resolve only against the acting player's hand. If several held copies share a name,
use a physical card id or hand reference. Saved actions always use hand references and explicit
qualifiers, so replay never depends on input aliases.

The outer phase actor resumes after another player's required answer. In a War military window,
`pass` proceeds to the recorded roll. Passing the Advances step forgoes further leader claims.
`pass` cannot skip Civil War losses, required replacements, War cessions or trade offers.
In Final Card Play, every non-burden card must be played before passing; Master Art cannot discard.
When immediate Master Art is enabled, acquiring it offers one `discard-card <reference>` or `pass`
before resuming the same purchase activity. This does not consume a later Buy Card discard.

## Authority outcomes and replay

| Entry | Request and value ordering |
| --- | --- |
| `!shuffle <card-id> ...` | Exact permutation of the current authority request: initial deck, next epoch plus eligible discards, setup returns, or delayed reserve reinsertion. Never a player command. |
| `!draw <player> <reference> <card-id>` | Delivers the requested top card and reference, both during setup and later draws. |
| `!roll capital-tie <player>=<die> ...` | One attributed die for each player in the current highest unresolved capital tie. Canonical text orders the player ids; tied subgroups request another roll. |
| `!roll competition <die> <die> <die>` | Competition dice in white, black, green order. |
| `!roll war <die> <die>` | War dice in initiator, opponent order. |
| `!roll shortage <die> <die> <die>` | Commodity dice first and second, shortage/surplus direction die third. |
| `!roll windmill <die>` | Wind/Watermill selection die. |
| `!trade <player> <player> <reference>` | Requested random card transfer: owner, recipient, then a reference currently in the owner's hand. |

Starting-card distribution (`INITIAL_DRAW`) follows the initial shuffle and precedes capital
bidding. The recurring `DRAW_CARD` phase includes first-player shortage/surplus cancellation and
then draws in turn order. Both stages deliver cards through the same `!draw` outcome, also used
for additional draws earned during play.

Every outcome must match the pending request, including participant identities, dice count, card
ownership, draw reference and deck top. Replay consumes recorded outcomes and generates no randomness.
Shuffles and private draws/transfers are redacted for unauthorized viewers; a public history view
is not a complete authority replay log. Storage revisions contain deltas that must be accumulated.
The current development format has no legacy command or outcome migration.
